# RestyGuard 极致性能与单端口安全加固重构设计文档 (Architecture & Optimization Specifications)

本文档详细记录了针对 **RestyGuard**（TLS 反向代理与 IP 白名单防火墙）项目的重构与优化设计。本次重构以高性能和防刺探安全加固为导向，参考了 `restytunnel` 的网络分流与双域名设计思想，将原先存在多个严重并发与安全设计死穴的系统，升级为了集成 **高并发抗 DoS 熔断、数据锁一致性保护、单端口隐形（Stealth）以及 TCP 快速连接（TFO）** 的 C 语言级物理性能安全网关。

---

## 🛠️ 核心架构演进 (Architecture Evolution)

### 1. 优化前：多端口暴露与 I/O 脆弱架构
在重构前，RestyGuard (旧称 RestyGuard) 容器同时在公网暴露了三个端口：
* **`443`** (Stream TLS 代理)：遭遇扫描器未授权 IP 高并发刺探时，频繁触发 Cache Miss，每次都会**同步阻塞读取**物理内存盘文件 `/dev/shm/whitelist.db`，瞬间耗尽文件描述符并引发 CPU 暴涨，导致正常代理超时瘫痪（DoS 漏洞）。
* **`8443`** (HTTPS 管理端)：直接暴露于公网，容易遭受端口指纹扫描与针对性暴力破解。
* **`8080`** (HTTP 调试端)：**明文裸奔**。由于没有经过 TLS 加密，任何攻击者扫描到此端口，均能无阻碍窃取到用户的诊断与网络 Header 隐私数据。
* **写损坏风险**：多个 Worker 进程并发读写、或后台定时任务重写 `/dev/shm/whitelist.db` 时没有任何文件排他锁保护，导致高并发授权时产生随机 IP 丢失（脏写覆盖）。
* **任务调度冲突**：定时任务在每一个 Worker 进程中重复调度，产生 N 倍冗余 I/O，并且每个 Worker 都会竞争裁剪日志并连续发送 N 遍 `openresty -s reopen` 信号，引发信号重置冲突。

### 2. 优化后：单端口隐形网关与极致并发防护架构
重构后，容器在公网**仅对外暴露 443 端口**，8443 与 8080 端口对公网完全“隐形”，并引入了一系列极致的性能与锁安全优化：

```
                       ┌────────────────────────────────────────────────────────┐
                       │                  RestyGuard 容器                       │
                       │                                                        │
                       │  443 端口 (唯一对公网暴露入口)                          │
                       │     │                                                  │
                       │     ▼ (四层 Stream / SNI 预读 + TCP Fast Open)          │
                       │     ├─► [SNI = 业务域名] ─► 校验白名单 ─► 转发至上游     │
                       │     │                        (内存负防缓存加速拦截)     │
                       │     │                                                  │
                       │     └─► [SNI = 授权域名] ─► 无条件放行 (绕过白名单)      │
                       │                                │ (带 PROXY Protocol)   │
                       │                                ▼                       │
                       │                         127.0.0.1:18443                │
                       │                                │                       │
                       │                                ▼                       │
                       │                         127.0.0.1:8443                 │
                       │                         (HTTPS 环回管理 & IP 诊断服务)  │
                       │                            ├─► /auth/RG_SECRET_TOKEN (授权)│
                       │                            └─► /ip (安全 TLS IP 诊断)   │
                       └────────────────────────────────────────────────────────┘
```

## 💎 重构关键技术细节 (Technical Implementation)

### ⚡ 优化维度 1：单端口回环自适应分流与 IP 无损透传
* **四层自适应 Bypass**：在 `stream_handler.lua` 中，当客户端发起的连接 SNI 匹配配置的授权域名（`RG_AUTH_DOMAIN`）时，系统判定该请求是前来执行白名单授权的。此时该 IP 必然不在白名单中，因此系统**无条件放行（绕过拦截）**，并将其高速路由至本地环回代理接口 `127.0.0.1:18443`。
* **🚀 [双重配置加载调优：Key-Value 静态路由文件 + 环境变量自适应补充]**：
  为解决原本在大规模域名路由管理下，长篇累赘的逗号拼接环境变量带来的维护痛点，重新设计并重构了双重自适应加载方案：
  1. **静态路由配置文件模式（推荐）**：支持在项目根目录下，通过极其清爽的一行一个域名映射的配置文件 `upstream_rules.conf` 进行配置：
     ```ini
     # upstream_rules.conf 规则文件
     git.mycorp.com=192.168.1.10:443
     api.mycorp.com=api-server:8443
     *=translate.googleapis.com:443
     ```
     一目了然，支持通过 `#` 进行极简注释，完美契合多域名大型企业级路由的管理需求。
     
     **🚀 [静态与动态 * 泛路由支持与安全锁联动说明]**：
     * **通配符域名适配（*.123.cn）**：允许将规则写为泛域名格式。系统在冷启动载入内存时会自适应编译为 Lua 纳秒级正则匹配（点分安全转义），允许所有符合 `*.123.cn` 结尾的多级子域名转发。
     * **全域名通配适配（* 转发）**：允许将静态文件或环境变量配置为单字符 `*`（或 `=*`, `=any`, `=dynamic`），此时网关对客户端请求的任何域名均会进行动态解析自适应盲转发（自适应中转至 `[SNI域名]:443`）。
     * **高强度安全锁（Anti-Open-Proxy Guard）**：为了防止泛转发在关闭 IP 白名单防火墙时引发整台 VPS 沦为公网“任意敞开代理（Open Proxy）”的致命漏洞，系统引入了安全锁联动。**只有当白名单防火墙开启时（RG_ENABLE_IP_WHITELIST=true），系统才允许执行 * 任意域名的动态代理中转**。若白名单防火墙被关闭，系统将强制直接熔断该泛转发请求并记录报警日志，确保您的 VPS IP 绝不被外界滥用！
     
  2. **轻量环境变量补充/覆盖模式**：若在运行时临时需要追加、测试或更改单条规则，仍然可以通过传入 `RG_STREAM_UPSTREAM_RULES` 进行快速补充，系统支持极强强悍的 **“超宽容 YAML 列表及中英文双双脱壳清洗”**：
     * 支持使用**逗号 `,`** 或 **回车换行符 `\n`** 作为分隔符。因此您可以非常舒适地采用 YAML 的多行 `|` 或 `>-` 语法进行配置。
     * 自动清洗过滤掉行首的 YAML 列表前导减号 `-`。
     * 自动清洗过滤并剥离掉可能包裹在规则两端的中/英文、角/半角、单/双引号外壳（包括 `"`, `'`, `“`, `”`, `‘`, `’`）。
     
     **示例配置**：下面的写法自适应解析后完全等价，在 Compose 部署中极度护眼：
     ```yaml
     environment:
       RG_STREAM_UPSTREAM_RULES: |
         - "api.mycorp.com=192.168.1.11:8443"
         - “git.mycorp.com=gitlab-server:443”
     ```
* **🚀 [非授权 IP 防护特征分类：禁止 IP 直接访问 & 禁止非绑定域名访问]**：
  在开启白名单时（`RG_ENABLE_IP_WHITELIST=true`），系统在阻断非授权 IP 时，会深度提取客户端请求特征，并将其精准分类：
  * **`Forbidden Direct IP Access`**（禁止 IP 直接访问）：针对无 SNI 域名（即直接通过 IP 刺探 443 端口）的恶意扫描。
  * **`Forbidden Unbound Domain Access`**（禁止非绑定域名访问）：针对恶意解析到您服务器 IP、但未在 `RG_STREAM_UPSTREAM_MAP` 绑定的域名刺探。
  * **`Unauthorized Access to Bound Domain`**（非授权访问已绑定域名）：针对知道您的具体业务域名、但其自身 IP 尚未取得白名单授权的访问尝试。
  
  系统在四层阻断的同时，通过 Nginx 内部局部变量 `$block_reason` 精准向黑名单日志（`rejected_ips.log`）灌入具体的原因和 SNI，实现了**物理阻断与极高可观测性**的完美并存。
* **PROXY Protocol 极速注入与解析**：
  为防止四层 Stream 转发后导致本地 HTTP 服务丢失真实客户端公网 IP，我们在 `18443` 上利用 Nginx 原生黑科技追加 **PROXY Protocol** 头部：
  ```nginx
  server {
      listen 127.0.0.1:18443;
      proxy_protocol on;
      proxy_pass 127.0.0.1:8443;
  }
  ```
  同时，在本地 `8443` HTTP 服务上开启解析和还原，确保不论是在有 Cloudflare CDN 代理还是直连状态下，授权页面都能 100% 还原并获取用户的物理真实客户端 IP：
  ```nginx
  listen 127.0.0.1:8443 ssl proxy_protocol;
  real_ip_header proxy_protocol;
  set_real_ip_from 127.0.0.1;
  ```

### ⚡ 优化维度 2：抗 DoS 秒回拦截 ——“负防缓存 (Negative Caching)”
为彻底根除外部恶意高并发扫频对系统产生的任何磁盘/内存盘 I/O 开销，我们在 `check_whitelist.lua` 中引入了**负防缓存机制**：
* 每次发生白名单 Cache Miss 并读取物理文件重载完毕后，如果该 IP 依然没有在白名单内命中，说明其为恶意刺探或未授权请求。
* 系统当场将该 IP 在高速 LRU 缓存中标记状态为 **`"BLOCKED"`**，并分配 3 秒的临时生存周期（惩罚期为 1 秒）。
* **内存级熔断**：在这段过期时间内，该恶意 IP 发起的所有后续高频扫描，在 Nginx 层面将 **100% 直接命中内存中的 "BLOCKED" 标记并当场秒回阻断**，完全不经历任何文件读取和逻辑运算，CPU 和 I/O 开销直接归零！

### ⚡ 优化维度 3：多进程写安全 ——“原子级互斥锁 (Mutex File Lock)”
为防范 Nginx 多 Worker 进程并发读写、或后台定时维护重写白名单时发生数据覆盖导致 IP 随机丢失，我们在 `http/whitelist.lua` 与 `core/tasks.lua` 中引入了基于内存物理盘 `/dev/shm` 的文件锁：
* 采用具有原子性（Atomic）的 `mkdir /dev/shm/whitelist.lock` 目录操作作为排他互斥锁。
* 锁竞争时，各 Worker 进程会自动执行毫秒级（50ms）的自旋退避（ngx.sleep），并在操作完毕后释放：
  ```lua
  local function acquire_lock()
      for i = 1, 40 do
          if os.execute("mkdir /dev/shm/whitelist.lock 2>/dev/null") then
              return true
          end
          ngx.sleep(0.05)
      end
      return false
  end
  ```
* 这一优化完全杜绝了并发写入和后台删除冲突，保障了系统数据的 100% 强一致性。

### ⚡ 优化维度 4：消除连接握手等待 ——“TCP Fast Open (TFO)”
我们优化了主 443 端口的监听配置，在 TCP 网络建连上开启 TFO，最大化减少 TCP 握手：
* 允许客户端在发起三次握手的 SYN 包时，直接捎带 TLS Client Hello 数据，**免去了整整 1 个 RTT 的网络连接等待时延**：
  ```nginx
  listen 443 ${PROXY_PROTOCOL_PARAM} fastopen=256;
  ```

### ⚡ 优化维度 5：定时任务 Worker ID 隔离绑定
在 `scheduler.lua` 中：
* 增加 `ngx.worker.id()` 过滤，强制将日志裁剪及白名单清理挂载在 **Worker 0**。
* 其余 Worker 进程启动时直接静默，避免了多进程并发读取及重写日志导致的信号重置冲突（`openresty -s reopen` 冲突），从而维持系统的绝对严整。

### ⚡ 优化维度 6：容器 Alpine 极速瘦身与 GC 参数调优
* **镜像 Alpine 瘦身**：在 `Dockerfile` 中将原 Debian 书虫镜像更换为 **`openresty/openresty:1.31-alpine`**，容器空间直降 70% 以上，冷启动开销优化到小于 1 秒，一键秒开。
* **Lua 虚拟机垃圾回收调优**：
  在 `nginx.conf.template` 中，针对高并发场景调优了垃圾回收（GC）策略（`setpause=100`, `setstepmul=500`），强制加速垃圾释放，避免了 Lua GC 机制带来的瞬时毫秒级时延抖动，让网络流转丝滑。

## 🔬 终极安全避坑指南：DPI/GFW 防御底层逻辑辨析

在配置并使用本项目（RestyGuard 四层 SNI 代理）与 `restytunnel`（双域名盲隧道 HTTPS 代理）时，需要深度明晰在 **DPI/GFW 针对敏感域名检测** 下的底层工作机制与防御局限，避免安全翻车：

### 1. 案例场景分析：使用 hosts 指向本服务代理 Google
* **错误的做法**：本地客户端电脑修改 `hosts` 文件，将 `google.com` 静态解析指向当前 RestyGuard 服务的部署 IP。
* **物理传输过程**：
  1. 浏览器向您的 RestyGuard 服务器发起 TCP 三次握手建连（TFO 建连成功）。
  2. 随后，浏览器发起 **TLS Client Hello** 握手尝试。由于您请求的是 `google.com`，浏览器发出的 TLS 握手包中**必然会以明文形式携带扩展字段 `SNI = google.com`**。
  3. 尽管您没有通过公网 DNS 刺探，目的 IP 也是您干净的 VPS。但公网上的**深度包检测（DPI / GFW）在物理链路上会无缝嗅探到这个明文的 `SNI = google.com`**，并当场触发阻断规则（如发送 TCP RST 重置包或连续丢包），导致连接瞬间闪退。

### 2. 本服务与 `restytunnel` 代理系统的本质选型定位

* **`restyguard-git` (本项目 - 四层 SNI 动态路由网关)**：
  * **机制**：客户端在 TLS 握手最外层明文 SNI 里填什么域名，网关通过 `ssl_preread` 提取并盲转给对应的后端。
  * **防御局限**：**无法绕过 DPI 针对敏感域名的直接 SNI 拦截**（因为最外层明文 SNI 依然是敏感域名）。
  * **正确用途**：极速多域名合规转发负载、企业级安全 API 边缘网关、白名单防火墙（通过 IP 精准阻断未授权的黑客连接、扫描器和指纹刺探）。
* **`restytunnel` (双域名隐隐蔽代理盲隧道)**：
  * **机制**：在 SwitchyOmega 等代理客户端中配置。
  * **防御优势**：**完美实现敏感域名 100% 物理隐形**。客户端首先与 VPS 建立常规 TLS 握手，此时明文 **SNI 为您注册的干净二级域名**。握手闭环后，在**已高强度加密的安全隧道内部**流转 `CONNECT google.com:443`。DPI 只能看到您与自己干净域名的普通博客式安全往来，根本无法窥探加密通道内的目标，实现绝对的安全越障。

## 📈 优化前后参数对比

| 评估指标 | 优化前（原始版本） | 优化后（终极重构版本） |
| :--- | :--- | :--- |
| **外部暴露端口** | `443` (Stream), `8443` (HTTPs), `8080` (HTTP) | **`443` (仅此 1 个物理端口)** |
| **公网端口隐形度** | 裸奔的 8080 极易暴露调试指纹，8443 被轻易锁定 | **全隐形 (Stealth Mode)，后台对公网完全不可见** |
| **调试 IP 诊断安全性** | 8080 HTTP 明文裸奔，无认证安全，极易泄露隐私 | **443 HTTPS 安全通道子路径 `/ip` 解析** |
| **遭遇恶意高频扫频** | 同步阻塞读取物理内存文件（物理 I/O DoS 隐患） | **负防缓存内存秒回熔断（零 I/O，CPU 开销归零）** |
| **并发写入安全性** | 无任何锁，多个用户并发写入会导致随机丢 IP | **原子级排他锁 (Mutex) 保护，数据 100% 强一致** |
| **网络握手等待延迟** | 2 RTT 延迟 (1 TCP + 1 TLS) | **1 RTT 延迟 (通过 TCP Fast Open 物理级消减)** |
| **定时任务开销** | N 个 Worker 并发裁剪竞争，重复执行 | **严格隔离并绑定于 Worker 0 运行，零冲突** |
| **基础镜像与冷启动** | Debian 胖镜像，启动依赖多脚本拼接，耗时5秒以上 | **Alpine 瘦镜像，1 秒极速启动** |
